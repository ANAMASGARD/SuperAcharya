# Email authentication contract research

Research only; no auth implementation, credentials, provider account, database, or deployment was changed. Inspected Agent-Native Core/Toolkit 0.226.0 and lockfile Better Auth 1.7.6. Existing `main` work was preserved. Library documentation was queried through the requested Context7 shell skill, then checked against installed code.

## Required behavior

Email signup must verify ownership. Every subsequent **email/password** sign-in must require a fresh emailed code after the password is accepted. Existing sessions remain valid; Google sign-in remains available. Email OTP passwordless sign-in does not satisfy this requirement.

## Installed integration and constraints

- `server/plugins/auth.ts` already owns bootstrap through public `runBetterAuthMigrations` and `autoMountAuth`, retaining the shared auth runtime and social-provider configuration. Keep this path and stable auth secret, cookie namespace, database, and session lifetime.
- `BetterAuthConfig` exposes `basePath`, `sessionMaxAge`, `socialProviders`, `plugins`, and `googleScopes`. It does **not** accept arbitrary top-level Better Auth options or hooks. Add supported Better Auth plugins through `betterAuth.plugins`; do not create a second auth instance or patch Core.
- Core normally installs `twoFactor({ allowPasswordless: true, accountLockout: { enabled: true } })`. A configured plugin with id `two-factor` suppresses the default, allowing one configured `twoFactor` with `otpOptions.sendOTP` and disabled TOTP if email-only is intended. Core already has the two-factor table and user flag migrations.
- Native `twoFactor` challenges only users with `twoFactorEnabled`. Merely configuring `sendOTP` does not make it mandatory. Its sign-in hook matches credential endpoints, not social callback routes, so preserving Google is compatible. It removes the newly created credential session before returning the pending challenge; do not implement a UI-only post-login check.
- The default Toolkit two-factor form posts to `/_agent-native/auth/two-factor/verify`, whose Core handler verifies an authenticator code. Email delivery/verification require a supported auth presentation customization using native Better Auth `/two-factor/send-otp` and `/two-factor/verify-otp` endpoints under `/_agent-native/auth/ba`. `renderSignInPage` is already a public mount option; inspect published ejection units before choosing an app-owned form. Never copy Core runtime internals.
- Core's deployment email readiness recognizes only Resend, SendGrid, and development transport. Its connection catalog has no Brevo entry. Declaring `auth.requireEmailVerification=true` without recognized email readiness disables password signup. Adding a Brevo callback alone does **not** fix this. This is an explicit implementation compatibility gate.

Evidence: [app bootstrap](../server/plugins/auth.ts), [auth config declarations](../node_modules/@agent-native/core/dist/server/better-auth-instance.d.ts), [Core policy and plugin construction](../node_modules/@agent-native/core/dist/server/better-auth-instance.js), [Core auth routes](../node_modules/@agent-native/core/dist/server/auth.js), [email provider types](../node_modules/@agent-native/core/dist/server/email.d.ts), [installed authentication guide](../node_modules/@agent-native/core/docs/content/authentication.mdx), [Toolkit auth presentation](../node_modules/@agent-native/toolkit/src/app/auth/AuthPage.tsx).

## Supported building blocks and required proof

Better Auth `emailOTP` can override signup verification with `overrideDefaultEmailVerification: true` and `sendVerificationOTP`; use hashed OTP storage, expiry, bounded attempts and resend rate limits. Its `/sign-in/email-otp` endpoint is passwordless and must be denied by server policy for this product. Disabling signup in that plugin does not disable passwordless login. Email verification and login second-factor challenges must stay distinct. [Email OTP documentation](https://github.com/better-auth/better-auth/blob/main/docs/content/docs/plugins/email-otp.mdx)

Better Auth plugins can contribute `init` options and auth middleware hooks. This is the candidate supported seam for the narrow mandatory policy: ensure new credential users are enrolled, apply policy to existing credential users on their next password login without revoking existing sessions, forbid user-driven disabling, forbid trusted-device bypass, and block alternative email passwordless routes. An alternative to persistent enrollment is a policy after-hook before native twoFactor that clones the successfully authenticated `newSession` user with `twoFactorEnabled:true` through `setNewSession`. Installed 1.7.6 checks this in-memory flag, and its pending-challenge verifier resolves the user from the signed challenge record without requiring a stored enrollment row. This is a promising no-bulk-migration approach, but hook ordering, type compatibility and complete-route behavior require an executable probe; it is not yet verified. Plugin ordering and existing-user handling must be demonstrated against 1.7.6 before implementation is considered sound. Do not mutate user flags for an email before its password is validated. Do not replace the framework's existing database hooks. [Plugin contract](https://www.better-auth.com/docs/concepts/plugins), [2FA documentation](https://github.com/better-auth/better-auth/blob/main/docs/content/docs/plugins/2fa.mdx)

`trustDevice:false` in the UI is insufficient: native 2FA accepts trusted-device requests and honors existing trust cookies. Enforce the every-login rule server-side on all verification routes and invalidate/ignore trust evidence through supported hooks. Likewise, turn off/deny magic-link entry if it would provide an alternative email login without the required password. Verify reset-password, signup auto-session, email-verification auto-session, backup codes, and direct Better Auth routes cannot bypass the intended policy.

Resolve the Brevo readiness mismatch explicitly through a supported plugin initialization/configuration extension or a documented upstream seam. The native email-OTP plugin demonstrates returning `emailVerification` options from `init`, but this alone does not repair Core's earlier readiness-derived signup disable flag or its compatibility route/UI policy. A compatibility probe must test both native and Core wrapper routes before committing to this approach. Missing support is a framework-extension blocker, not justification for dummy provider credentials or modifying `node_modules`.

## Brevo delivery contract

Use server-side HTTPS `POST https://api.brevo.com/v3/smtp/email` with `api-key` and JSON headers. For direct content send a configured verified sender, one `to` recipient, subject, `htmlContent` and/or `textContent`. The send guide documents HTTP 201 with `messageId`; this proves provider acceptance, not inbox delivery. The installed native two-factor send handler catches rejected `sendOTP` promises and can return `status:true` after failure; explicitly prove supported failure propagation or return truthful delivery state through a narrow supported wrapper before shipping. Use a bounded timeout and sanitized failures; never log OTPs, credentials or entire email bodies. No SDK is necessary for one validated fetch adapter. Keep credential resolution deployment-scoped because pre-login visitors have no authenticated workspace identity. Inspect the existing scoped secret resolver and register a dedicated Brevo connection rather than using arbitrary user secrets. Sender/domain authentication and live delivery were not checked. [Brevo send guide](https://developers.brevo.com/docs/send-a-transactional-email), [API reference](https://developers.brevo.com/reference/send-transac-email)

## Implementation acceptance gates

1. Prove plugin/config initialization, signup/readiness and both auth endpoint families on an isolated test database; preserve Google configuration and session cookies.
2. Test new and existing credential accounts: no usable session before code, wrong/expired/replayed codes rejected, bounded resend and attempts, successful code grants exactly the intended session.
3. Attack direct endpoints: passwordless email OTP, magic link, disabled-2FA, trusted-device requests, reset and verification auto-sign-in, cross-user challenge reuse, and concurrent retries.
4. Confirm a pre-existing session still works and Google callback remains unchanged. Browser-test signup, password plus code, resend, refresh/back, delivery failure and authenticated whiteboard landing.
5. Run configured typecheck, focused tests, doctor and build. There is no configured lint script. This research performed source/doc inspection only, no runtime or live email validation.

## Implementation probe correction

The executable 1.7.6 OTP verification probe disproved the proposed in-memory-only enrollment approach: the OTP endpoint also checks the persisted `twoFactorEnabled` flag and refuses a session without it. The implementation instead updates that flag only after successful password verification, then lets the native two-factor hook delete the provisional session. A delivery after-hook converts swallowed provider failures to HTTP 503. Plugin init mutates the public initialization options explicitly because returned option defaults cannot override Core's existing values. Real Core/PGlite tests exercise signup, verification, credential challenge, OTP completion and the database-backed resend limit.

CLI 2.6.1 supports private M2M app creation with `transactional.email:write`; browser login produces developer OAuth credentials, not a permanent API key. The deployment adapter supports both an API key and dedicated M2M client credentials. [Brevo M2M](https://developers.brevo.com/docs/oauth-m2m-authentication)
